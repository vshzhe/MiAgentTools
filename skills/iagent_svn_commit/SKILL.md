SVN 提交注释生成与执行（iagent_svn_commit）—— 四环节确认提交 + 提案分类提交。

**输入**：`/iagent:svn-commit` 后可跟变更列表名、点名文件或「提交 <提案名> 提案」；省略时先自动检测活跃提案，无活跃变更再询问是否提交全部。

## ⚠️ 强制约束

- 仅由显式调用 `/iagent:svn-commit` 触发；普通文本提交请求不触发。
- 四个确认环节缺一不可：提交范围、提交内容清单与功能描述、知识库推送、最终确认；任何环节未经用户确认不得推进，最终确认通过前绝不执行提交。
- 执行中只允许 `svn add`、写注释与路径清单文件、SVN 提交、只读验证，以及向知识库 MCP 提交经确认的文件；禁止改业务代码。
- 密码只进内存与 stdin，禁止显示、进命令行或写日志；失败一次即停。

## 使用样例

```text
场景 1 指定变更列表（提交该列表下的文件）：
/iagent:svn-commit 提交 audit-export 列表
→ 候选集 = 该列表成员，逐环节确认后提交，汇报版本号与验证结论

场景 2 均未指定：
/iagent:svn-commit
→ 先按「提案判定」自动检测活跃提案，无活跃变更时询问是否提交全部变更代码，确认后逐环节推进

场景 3 直接点名文件：
/iagent:svn-commit 提交 AuditController.java 和 AuditServiceImpl.java
→ 候选集 = 点名的文件，逐环节确认后提交

场景 4 提案点名（分类提交）：
/iagent:svn-commit 提交 add-audit-alert 提案
→ 读取该提案 → 变更自动归类功能代码/测试代码/文档 → 生成 N 笔分类提交计划（各带前缀与溯源标注）
→ 逐环节确认后依次执行，每笔提交信息尾行自动标注「提案: add-audit-alert」
```

## 提案分类提交（场景 4 专属能力）

### 提案判定

- **点名提案**：校验 `openspec/changes/<提案名>/` 存在 → 读取其 proposal/design/tasks 进入分类提交流程；提案名不存在时列出当前活跃变更供用户选择；提案已在 `openspec/changes/archive/`（归档）时同样读取归档提案内容并按分类提交流程推进，同时在环节 1 提示「提案已归档，按提案内容检查未提交变更」；若 `svn status` 无相关变更则提示无需提交并终止。
- **未点名**：自动检测 `openspec/changes/` 活跃变更——唯一时直接采用并提示；多个时列出供用户选择；无活跃变更时退化为场景 2（询问是否提交全部，提交不带溯源标注）。
- 提案名仅允许取自 changes/ 目录实际存在的变更名（或用户从列表中的选择），禁止拼接任意路径。

### 三类自动分类（路径优先）

| 类别 | 判定规则 | 提交前缀 |
| --- | --- | --- |
| 测试代码 | `src/test/**`、`test/**` 下任何文件（含 *.md 测试说明）；或独立测试文件名匹配 `*Test.java`、`*Tests.java`、`*.test.*` | 固定 `test` |
| 文档 | 已纳管版本化的 `docs/**` 下任何文件；其余位置 `*.md`；已版本化纳管的 openspec/ 变更制品 | 固定 `docs` |
| 功能代码 | 其余产出（源码、页面、SQL 脚本、配置文件） | 按变更性质判定 `feat`/`fix`/`refactor`/`perf` 等 |

- 路径优先：目录语义覆盖扩展名（src/test/ 下的 *.md 归测试代码，docs/ 下的 *.java 示例归文档）；不在测试/文档目录的才按扩展名判定。
- 未纳管（?）的 docs/openspec/ 文件遵循「提交范围排除」默认不提交、不自动 svn add；用户明确点名要求时以用户指令为准纳入并归文档类。
- 交叉校验辅助：提案 tasks.md 的任务类型标签（[代码]/[测试] 等）作为归类参考，与路径规则冲突时以路径规则为准并在清单中说明。
- 某类为空时跳过该笔提交，在计划与汇报中说明。

### 溯源标注

- 分类提交的每笔提交信息：主体保持单行前缀格式，另起尾行标注 `提案: <变更名>`。
- 示例：

```text
feat: 审计管理-告警展示: 新增告警批量处理逻辑
提案: add-audit-alert
```

- 非提案场景（场景 1/2/3 及场景 4 退化）不带溯源标注。

### 提案关联校验（辅助检查，不阻断）

- 分类时对每个候选变更文件与提案内容（proposal/design/tasks 中的文件路径、任务描述、涉及模块）做关联校验。
- 无关联的变更不纳入分类提交计划，在环节 2 清单单独列出「与提案无关的变更」并展示校验依据，请用户逐项决定纳入或排除。
- 校验不阻断流程，最终由用户裁决。

### 分类提交执行

- N 笔提交依次执行（建议顺序：功能代码 → 测试代码 → 文档），每笔独立走「提交执行阶段」流程。
- 任一笔失败即停：不继续后续类别、不自动回滚已成功笔（SVN 已提交无法本地回滚），汇报已完成笔/未执行笔及失败原因，由用户决定后续。
- 每笔提交后执行双验证通过再进下一笔。

## 交互流程（逐环节确认）

> 所有询问使用 ask_user_question 工具（不可用时直接向用户提问）；未获用户明确答复不得推进下一环节。用户可随时明确要求终止：终止即停止，不执行任何提交。环节 1 确定候选集后，先按「工作流程」读取变更、核对菜单并生成功能描述，再进入环节 2。

### 环节 1：确定提交范围（四种场景）

变更列表即 SVN changelist：`svn changelist <列表名> <路径…>` 创建/调整、`svn changelist --remove <路径>` 解除，每个列表对应一组文件；`svn status` 将成员归入 `--- Changelist '<列表名>'` 分组。列表是纯客户端分组，不影响仓库内容。

- **场景 1 指定变更列表**（指定即表示提交）：校验列表存在 → 候选集 = 该列表全部成员；列表不存在时列出 `svn status` 中当前可用的变更列表供用户选择。
- **场景 2 均未指定**：先按「提案判定」未点名分支自动检测活跃提案——存在活跃变更时依该分支进入提案分类提交流程；无活跃变更时询问「是否提交全部变更代码？」——确认后候选集 = 全部变更（含各变更列表成员，列表只是分组不是排除）；答复不提交全部时请用户指定列表或文件，仍无法确定则终止。
- **场景 3 直接点名文件/类**：候选集 = 点名的文件；点名的排除清单内文件按用户指令处理，但须在清单中显著标注。
- **场景 4 提案点名**：按「提案判定」确定提案 → 读取提案 → 按「三类自动分类」归类 → 生成 N 笔分类提交计划（各带前缀与溯源标注）。

候选集先经「提交范围排除」过滤，再进入环节 2。

### 环节 2：提交内容清单与功能描述确认

- 展示过滤后的提交内容清单（M/A/D 分组、被引用自动纳入的新文件、排除统计）。
- 提案场景额外展示：N 笔分类提交计划（每笔的类别、前缀、文件分组、溯源标注）、「与提案无关的变更」待裁决清单。
- 按前缀规范生成每笔的功能描述（提交注释）。
- 询问「提交内容清单和功能描述是否需要修改？」：需要 → 按用户意见修订后再次询问；不需要 → 进入环节 3。

### 环节 3：知识库推送询问

- 询问「本次功能是否推送知识库？」
- 推送 → 由提交人列出要推送的文件名称并逐项确认，形成「知识库推送清单」；未经提交人确认的文件不得推送。清单随环节 4 一并最终确认，实际提交在「提交执行阶段」第 6 步执行。
- 不推送 → 跳过。

### 环节 4：最终确认与提交

- 完整展示：提交内容清单、功能描述、知识库推送清单（如有）、排除统计；提案场景展示 N 笔分类明细。
- 询问最终确认：无疑问 → 进入「提交执行阶段」；有疑问 → 修订后再次询问，循环直到用户确认无疑问。

## 工作流程（读取与生成规则）

1. 确认 SVN 工作副本：`.svn` 存在或 `svn info` 可用，否则说明不适用并终止。
2. 候选集确定后仅对其读取变更：`svn status` / `svn diff`；必要时读取文件内容理解业务含义与菜单归属。
3. 提案场景：读取提案的 `change.json`（proposal/design/specs 段）+ `tasks.json` 理解功能范围、涉及文件与任务类型标签，用于分类与关联校验（存量变更无 change.json 时回退 proposal.md/design.md/tasks.md）。
4. 菜单名取真实菜单：优先从 Controller 的 `@SystemLogAnn(opmodule = "…")` 注解核对，其次看页面标题/导航；禁止编造、简写。页面未改但后台逻辑归属某菜单功能时同样标注该菜单；仅无页面引用、无菜单归属的纯接口才不带菜单；仍无法确定归属时询问用户确认。
5. 按前缀规范生成功能描述，进入「交互流程」环节 2。

## 提交范围排除（最高优先级）

target 目录（任意层级及其全部内容，含 classes、test-classes、surefire-reports、generated-sources 等）、任何位置的 *.class 编译产物、surefire-reports 测试报告、*.log 运行日志，以及 .idea、docs、本地脚本等未纳管非源码文件，一律不进入提交范围清单、不参与注释提炼、永不 svn add，即使被提交集内文件引用也不添加，本规则优先级高于「被引用则 add」；未纳管（?）的 openspec/ 变更制品同样默认不提交。src/test/java 测试源码不在排除范围，正常提交。排除项按 svn status 状态处理：?（未纳管）直接忽略，不算引用缺漏；A（已被 svn add）为危险项，禁止被裸目录提交带上——不提交、不 revert，改用过滤后的显式路径提交，并在汇报中提示用户手动 svn revert 撤销误加调度；M（已版本化）属历史误提交——不提交、不改动，汇报中单独列出并建议 svn delete。过滤后无剩余变更时不生成注释、不执行提交，说明全部变更均被排除；用户明确点名要求提交排除项时以用户指令为准；提案 tasks 列出的产出文件命中本排除规则时同样以排除优先、汇报中说明；汇报中统计排除的文件/目录数量。

## 提交前缀规范

| 前缀 | 含义 |
| --- | --- |
| feat | 新增功能 |
| fix | 修复 bug |
| docs | 仅文档、注释修改 |
| style | 代码格式调整（空格、换行、格式化，不改变业务逻辑） |
| perf | 性能优化 |
| test | 新增 / 修改单元测试、接口测试 |
| build | 构建脚本、打包、依赖配置变更（maven、gradle 等） |
| chore | 杂项：工具、脚本、静态资源，不改动业务代码 |
| revert | 回滚上一次提交 |
| refactor | 代码重构，不新增功能、不修复 bug |

## 输出要求

1. 改动关联页面菜单时，格式为【前缀: 一级菜单-二级菜单: 业务描述】。菜单名称必须为系统真实菜单，文字、名称与系统菜单保持一致，禁止编造、简写菜单。单菜单示例：`fix: 审计管理-告警展示: 修复分页异常`。提交内容涉及多个二级菜单时，必须分别罗列每个菜单下的功能描述（同一行内以分号分隔），禁止精简、合并为 1 个菜单；多菜单示例：`fix: 审计管理-告警展示: 修复分页异常；审计管理-日志导出: 修复导出乱码`。
2. 页面未修改、但改动的是某菜单功能的后台逻辑时，仍按【前缀: 一级菜单-二级菜单: 业务描述】标注所属菜单，便于快速定位功能归属。示例：`feat: 审计管理-告警展示: 新增告警批量处理逻辑`。
3. 纯后台接口（无页面引用、无菜单归属）才使用【前缀: 业务描述】，描述须写明是什么接口、做了什么操作。示例：`feat: 新增主账号批量查询接口，支持按部门过滤`。
4. 一次变更只能选择一个 type 前缀，禁止组合多个 type；描述为业务层面简洁文字，不要罗列底层代码改动；不要额外增加(模块)；默认只输出单行提交注释；仅当变更存在重要业务背景时，可换行增加简短补充说明。
5. 提案分类提交的每笔提交：主体保持上述单行格式，另起尾行标注 `提案: <变更名>`（见「溯源标注」）。
6. 执行提交时，提交后按「提交执行阶段」第 7 步汇报。

## 提交执行阶段

> 前置：交互流程第 4 环节最终确认通过后进入。分类提交场景：N 笔依次执行，每笔独立完成第 1-5 步，任一笔失败即停（见「分类提交执行」）。

### 1. 提交集完整性检查（防仓库编译断裂，必做）

- `svn status`：`M/A/D` 为提交集；`?` 为未纳管，默认不提交。
- `?` 源码文件被提交集内文件 import / 引用的，必须一并纳入提交（先 `svn add`，否则他人 checkout 后编译必断）；这类自动纳入必须先出现在环节 2 清单中并经用户确认。
- 未被引用的 `?` 不提交；具体范围与处理以「提交范围排除」为准。

### 2. 注释落盘（编码安全）

- 写 UTF-8 无 BOM 文件：`[IO.File]::WriteAllText($p, $msg, (New-Object System.Text.UTF8Encoding($false)))`，读回校验中文完好。
- 提交必须带 `--encoding UTF-8 -F <文件>`；禁止裸 `-m` 传中文。

### 3. 证书与凭据（内网 HTTPS 库常见坑）

- `E230001`（自建 CA、IP 访问致主机名不匹配）→ 加 `--trust-server-cert-failures unknown-ca,cn-mismatch`。
- `E215004`（认证失败但本机有缓存凭据）→ 从 `%APPDATA%\Subversion\auth\svn.simple\` 按 `svn:realmstring` 匹配取用户名；密码为 Base64 + DPAPI/CurrentUser，解密后经 stdin 传入：

```powershell
Add-Type -AssemblyName System.Security
$pass = [Text.Encoding]::UTF8.GetString([Security.Cryptography.ProtectedData]::Unprotect([Convert]::FromBase64String($b64), $null, 'CurrentUser'))
```

- 全程 `--non-interactive`，失败快速返回；密码只进内存与 stdin，禁止显示、进命令行或写日志，失败一次即停。

### 4. 执行提交

```powershell
$pass | svn commit --encoding UTF-8 -F <注释文件> --trust-server-cert-failures unknown-ca,cn-mismatch --username <用户> --password-from-stdin --non-interactive [路径...]
```

- 凭据按需套用：工作副本缓存认证可直接提交时，用 `svn commit --encoding UTF-8 -F <注释文件> --non-interactive` 即可；遇 `E215004` 等认证失败才走第 3 步的凭据解密路径并套用完整模板。
- 指定变更列表提交：最终清单与纯列表成员一致时可用 `svn commit --changelist <列表名>`（默认提交后自动移除该列表关联，需保留时加 `--keep-changelists`）；清单含列表外的自动纳入文件（被引用的新文件）时，必须展开为显式路径提交。
- 提交路径必须与最终确认清单一致：默认显式路径提交（路径多时用 `--targets <清单文件>`，一行一个路径，编码先验证）。
- 仅当确认清单覆盖全部已调度项且不存在被排除的 `A` 调度时，才可省略路径参数；实测裸目录提交会带上全部已调度项（含变更列表成员），故「提交全部」以外的场景一律用显式路径或 `--changelist`。

### 5. 提交后双验证

- `svn status`：本次提交集内无 M/A/D 残留（仅剩 `?` 与未纳入本次提交的其他变更，如其他变更列表成员——属预期保留，不算提交失败）。
- `svn log -r <新版本号> --xml`：XML 恒定 UTF-8，确认消息无乱码；控制台显示乱码 ≠ 存储乱码，禁止误判。

### 6. 知识库提交（如有）

- 仅当环节 3 已确认「知识库推送清单」时执行；SVN 提交失败时不执行，先处理失败。
- 提交前可调用 `mcp__llm-wiki__llm_wiki_status` 确认知识库 API 可达与当前项目。
- 调用 `mcp__llm-wiki__llm_wiki_import_sources`：paths = 经提交人确认的文件清单，可选 `destination_folder` 归档目录（如 sprint/2026-07）；单次最多 5 个文件，超出分批提交。
- 返回 submission_id 后即为「已提交待审核」：文件须经管理员审核通过才正式入库；可用 `mcp__llm-wiki__llm_wiki_submission_status` 查询审核状态与驳回原因，结果纳入汇报。
- 知识库 MCP 工具不可用或提交失败时如实说明，不影响 SVN 提交结果的汇报。

### 7. 汇报

- 通用：版本号、作者、路径数（M/A/D 分项）、使用的变更列表名（如有）、双验证结论、排除的本地文件清单、知识库提交结果（如有：submission_id 与审核状态）。
- 提案分类提交额外汇报：各笔分类明细（类别、前缀、文件数、溯源标注）、失败笔与未执行笔（如有）及失败原因。
