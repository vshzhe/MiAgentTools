检查变更提案完整性与实现合规性——深度代码库探索、8 维度完整性检查、合规性验证、量化评分与遗漏场景补充。在 /iagent:spec-propose 创建提案后，或经过 /iagent:spec-explore 探索分析后，使用此 skill 验证提案是否完整覆盖需求场景、是否符合项目规范。确保每个变更提案都经过完整性验证和合规性检查后再进入实现阶段。

本 skill 通过多维度检查确保：
1. 需求场景完整覆盖（无遗漏）
2. 实现方式符合项目规范
3. 代码设计符合框架模式
4. 安全性和性能考虑充分

## Phase 1: 加载变更提案

```bash
iagent spec status --change "<change-name>" --json
```

获取变更状态后，按以下顺序读取提案证据（Markdown 优先）：
- `proposal.md` - 需求背景和目标（Why / What Changes / Capabilities / Impact）
- `design.md` - 技术设计（Context / Goals / Non-Goals / Decisions / Risks）
- `specs/**/*.md` - Delta 规格（`### Requirement:` + `#### Scenario:`）
- `tasks.md` - 实现任务清单（编号 / 类型 / 状态 / Spec Ref / 节点标注）
- **降级（WARN，仅存量 / 已归档变更）**：变更只有历史 `change.json` / `tasks.json` 时只读降级读取并注明 WARN

下文各阶段提到的 proposal / design / specs / tasks 均按上述 Markdown 优先口径读取（历史 JSON-only 降级时注明 WARN）。

## Phase 2: 深度代码库探索（关键改进）

**这一阶段是确保提案完整性的核心，必须实际阅读相关代码。**

### 2.1 调用链分析

对于提案涉及的核心功能，必须追溯完整的调用链。使用 Grep 工具搜索符号定义与调用点（不绑定特定语言扩展名与路径），结合 Read 工具阅读关键文件。

**检查项**：
- [ ] 入口点（入口层：Action/Controller/路由处理器）是否明确
- [ ] 业务逻辑层（Service）是否涉及
- [ ] 数据访问层（DAO）方法是否完整
- [ ] 跨模块调用是否考虑

### 2.2 数据流分析

追踪数据从输入到输出的完整流程：

**检查项**：
| 数据流节点 | 检查内容 |
|-----------|---------|
| 输入来源 | 前端表单参数、API请求、数据库查询结果 |
| 中间处理 | 参数校验、类型转换、业务计算 |
| 输出去向 | 数据库写入、前端响应、日志记录 |
| 异常分支 | 校验失败、数据不存在、异常处理 |

### 2.3 现有实现模式分析

用 Grep 工具搜索项目中类似功能的入口层（Controller/Action/路由处理器）与数据访问层实现，对比提案中的实现方式。

**目的**：确保提案中的实现方式与项目现有模式一致。

## Phase 3: 多维度完整性检查

使用以下检查清单逐一验证（8 个维度，按项目实际分层对照）：

### 3.1 参数配置维度（6 场景）

| 场景 | 检查点 | 常见遗漏 |
|-----|-------|---------|
| 参数值为 `true` | 开启行为是否完整 | 是否需要记录日志 |
| 参数值为 `false` | 关闭行为是否完整 | 日志内容和级别 |
| 参数未配置 | 默认行为（通常视为关闭） | 是否有日志提示 |
| 参数值大小写变体 | 项目仅匹配小写 "true" | `TRUE`/`True` 处理 |
| 参数值非法格式 | "yes"/"1" 等应视为关闭 | 明确处理方式 |
| 参数查询异常 | 数据库异常返回空字符串 | 异常处理方式 |

### 3.2 输入输出维度（7 场景）

| 场景 | 检查点 | 常见遗漏 |
|-----|-------|---------|
| 输入为空 | null、空字符串、空集合 | 日志级别和响应 |
| 输入为空格 | 纯空格字符串 | trim处理后判断 |
| 输入超长 | 超过字段长度限制 | 截断或拒绝 |
| 输入特殊字符 | XSS/SQL注入风险字符 | 过滤和转义 |
| 输入格式错误 | 日期、数字格式不匹配 | 错误提示 |
| 输出为空 | 查询结果为空 | 空列表处理 |
| 输出超量 | 大数据量返回 | 分页处理 |

### 3.3 数据库操作维度（6 项）

| 场景 | 检查点 | 常见遗漏 |
|-----|-------|---------|
| SQL参数化 | 是否使用参数化查询/占位符 | 禁止字符串拼接 SQL |
| 事务边界 | 事务范围是否明确 | 业务层控制 |
| 并发更新 | 同一记录并发修改 | 版本号或锁机制 |
| 批量操作 | 批量插入/更新 | 分批提交、事务大小 |
| 数据迁移 | 表结构变更 | 迁移脚本、回滚方案 |
| 索引影响 | 新增查询是否有索引 | 性能评估 |

### 3.4 前端交互维度（6 项）

| 场景 | 检查点 | 常见遗漏 |
|-----|-------|---------|
| 权限检查 | 入口层权限检查机制完整 | 缺少请求上下文参数 |
| 表单验证 | 前端JS验证 + 后端验证 | 双重验证 |
| 分页标签 | 分页组件完整结构 | 分页参数回传字段 |
| 数据绑定 | 项目数据访问组件方法规范 | 列名/字段名大小写 |
| 浏览器兼容 | 符合项目浏览器兼容要求 | （语言/框架专项见下文） |
| 错误提示 | 错误信息展示方式 | alert或页面提示 |

### 3.5 错误处理维度（5 项）

| 场景 | 检查点 | 常见遗漏 |
|-----|-------|---------|
| 业务异常 | 抛出项目统一业务异常类型 | 错误信息和跳转页面 |
| 系统异常 | 抛出项目统一系统异常类型 | 异常堆栈记录 |
| DAO异常 | 数据未找到异常处理 | try-catch + 日志 |
| 外部调用 | 超时、重试机制 | 降级方案 |
| 异常恢复 | 可恢复异常处理 | 状态恢复 |

### 3.6 日志记录维度（5 项）

| 检查项 | 规范要求 | 常见问题 |
|-------|---------|---------|
| 日志级别 | INFO(正常)、WARN(警告)、ERROR(错误) | 级别选择不当 |
| 日志格式 | 包含业务上下文，变量用 `[]` 包裹 | 缺少上下文 |
| Logger声明 | 符合项目日志框架的声明规范 | 声明不规范 |
| 敏感信息脱敏 | 密码、密钥等不记录明文 | 信息泄露风险 |
| 异常日志 | 异常日志包含完整堆栈 | 缺少堆栈 |

### 3.7 安全性维度（6 项）

| 检查项 | 规范要求 | 常见遗漏 |
|-------|---------|---------|
| SQL注入 | 参数化查询，禁止拼接 | 字符串拼接 SQL |
| XSS防护 | 输入过滤，输出转义 | 特殊字符处理 |
| CSRF防护 | Referer验证，POST操作 | 白名单配置 |
| 权限控制 | RBAC权限检查 | 操作权限遗漏 |
| 密码处理 | 加密存储，传输加密 | 明文处理 |
| 敏感操作 | 审计日志记录 | 操作未记录 |

### 3.8 兼容性维度（4 项）

| 检查项 | 规范要求 | 常见问题 |
|-------|---------|---------|
| 语言运行时兼容 | 符合项目语言版本特性约束 | （专项：按项目声明的运行时版本） |
| 浏览器兼容 | 符合项目浏览器兼容要求 | （专项：按项目声明的浏览器兼容级别） |
| 数据库兼容 | 符合项目数据库 SQL 方言 | （专项：按项目实际数据库方言） |
| 配置兼容 | 配置项向后兼容 | 新增必填参数 |

## 语言 / 框架专项检查（按项目实际信息）

**触发条件**：检测到语言/框架项目特征（如 `pom.xml` / `build.gradle`、`web.xml`、`package.json`、JSP/Vue 页面、`.java` / `.ts` 源码等）时执行本节的检查**类别**；非对应项目跳过本节。

**取值来源（MUST）**：本节各检查项的**具体判据 MUST 来自项目初始化时固化的实际信息**，禁止假设固定框架、包名或版本：

1. 优先读 `.iagent/config.yaml` 的 `context` 段（技术栈、分层约定、包名规范、运行时/浏览器/数据库版本）与 `.iagent/rules/*.md`（按类型规则）
2. `context` 未覆盖时，从项目既有源码与配置探测：构建文件（`pom.xml` / `build.gradle` / `package.json` 的版本与依赖）、包路径、`web.xml`、路由/配置文件、既有同类实现
3. 探测结论标 **[待确认]** 请用户确认；确认后写回 `.iagent/config.yaml` 的 `context`，供后续技能复用
4. 仍无法确定时按「与项目既有同类实现保持一致」处理，MUST NOT 套用外部框架默认值

### A. 包结构与命名规范（判据按项目实际）

- 包名、类/方法/常量命名符合项目实际包结构与命名规范（从 `.iagent/config.yaml` context 或既有源码包路径推导）
- 表名、列名的大小写与命名风格与既有库表/实体一致

### B. 语言版本特性约束

- 仅使用项目声明的运行时版本所支持的特性（按构建文件的 `source`/`target` 或项目声明）
- 不引入目标版本不支持的新语法 / 新 API

### C. 日志框架

- Logger 声明与调用符合项目实际日志框架规范（从既有类导入与用法提取）
- 异常日志包含堆栈；日志变量带上下文标识；敏感信息不记明文

### D. 数据访问

- 使用项目实际数据访问组件与参数化方式；禁止字符串拼接 SQL
- 字段/列名大小写与既有实现一致；分页按项目既有方式，不手写方言分页
- 更新/删除操作有异常处理与明确事务边界

### E. 异常体系

- 使用项目统一异常类型（业务异常 / 系统异常 / 数据不存在等按项目实际类名）
- 各异常分支有明确处理与日志

### F. 前端页面

- 页面结构、组件库、分页、表单提交、权限检查与项目既有页面保持一致
- 浏览器兼容级别按项目声明（需兼容旧浏览器时避免其不支持的语法与布局）
- 需要页面模板时 MUST 从项目既有页面提取，MUST NOT 引入外部框架模板

### G. 数据库方言

- SQL 语法符合项目实际数据库方言；特殊字符转义、分页、序列/主键生成按既有实现

### 通用要求（与框架无关）

- **状态流转**：遍历业务状态全部可能值（含未知值兜底分支），每个分支有明确处理；未知值记录告警，不静默忽略
- **批量处理**：分批提交、记录成功/失败计数、单条失败不中断整批并记录上下文
- 具体状态码取值、日志 API、事务写法 MUST 与项目既有实现一致

> 本节**不内置任何特定框架 / 产品**（如内部自研框架、Struts、DWR、特定数据库）的硬编码模板与包名；项目实际框架细节由 `.iagent/config.yaml` 与既有源码提供。变更涉及的框架若未在 `context` 中登记，先补登再检查。

## Phase 9: 发现遗漏时更新文档

发现遗漏场景后，按优先级更新：

1. **P0 必须补充**（影响功能正确性，Markdown-first）：
   - 更新 `specs/<capability>/spec.md`：新增或修订 Requirement 与 `#### Scenario:`
   - 更新 `design.md` 的 Decisions：补充遗漏的设计决策
   - 更新 `tasks.md`：新增对应的实现任务（`Spec Ref` 指向补充的需求）
   - 更新后运行 `iagent spec validate --change "<name>"` 校验
   - **降级（WARN）**：历史 JSON-only 变更只读解析，MUST NOT 编辑 JSON，并在报告中注明 WARN
   - 示例（写入 specs 段的操作与场景）：
     ```markdown
     ### Requirement: 编辑场景数据处理

     #### Scenario: 编辑时替换而非累积配置
     - **WHEN** 用户编辑配置数据并保存
     - **THEN** 系统先删除旧配置数据
     - **AND** 然后保存新配置数据，确保数据替换而非累积
     ```

2. **P1 建议补充**（影响健壮性）：
   - 添加边界条件处理
   - 添加异常处理场景
   - 添加并发安全处理

3. **P2 可选补充**（影响体验）：
   - 添加日志优化
   - 添加性能优化
   - 添加用户体验改进

| 遗漏类型 | 出现频率 | 检查位置 | 标准修复 |
