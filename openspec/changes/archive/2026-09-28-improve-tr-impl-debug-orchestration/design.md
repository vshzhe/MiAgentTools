## Context

`venus_tr_impl_debug` 是 tr_impl 类型的编排层技能，正文唯一源在 `src/core/templates/workflows/tr-impl-debug.ts`（579 行）。本次改动涉及 Phase 2 排查阶段的路径选择与 Phase 7 收尾阶段的需求文档产出。

**既有架构现状（探索阶段 CodeGraph + Grep 交叉验证）**：

- **Phase 2 排查分层**：`2.2.0` status 预检（强制首动作）→ `2.2.1` `codegraph_files` → `2.2.2` `codegraph_search` + `codegraph_context` → `2.2.3` `codegraph_callers`/`codegraph_callees` + `codegraph_impact` → `2.2.4` 深度探索（`codegraph_explore` + 6 维根因深度分析）。其中 2.2.4 的触发条件是**事后**单判据：*"常规查询无法定位单一高置信根因"*（`:171`）。
- **Phase 7 收尾**：`7.1` 调 `venus_spec_verify_proposal` 打分 → `7.2` FAIL 自动修复循环 → `7.3` PASS 后调 `venus_tr_impl_review_proposal` 深度复查，再**无条件**调 `venus_tr_docs_requirement_doc` 非交互生成需求文档（`:402-408`）。
- **需求文档 skill 侧规则**：`venus_tr_docs_requirement_doc` 自身规定 *"When the target file already exists, overwrite it silently — regeneration is idempotent"*（`tr-docs-requirement-doc.ts:216`），并在 :203-214 按归档状态路由输出路径。
- **同构逻辑分布**：另有三处编排技能在验证通过后同样无条件生成需求文档——`tr-impl-workflow.ts:1382,2191`、`tr-impl-auto-workflow.ts:510,591,648`、`tr-impl-genfull.ts:193`。
- **命令派生双轨制**：`spec-*` 类指令正文经 `deriveCommandContent` 从 skill 正文自动派生；**4 个 tr_impl 技能（含 debug）的指令正文为手写压缩版**，改 skill 正文 MUST 手工同步（能力记忆 `tr-workflow-suite-skills/explorations.md` 已两次记录该陷阱）。
- **共享模块**：`src/core/templates/prompt-gate.ts`（缺陷五维提示词校验门）与 `flowchart-gate.ts`（缺陷链路版流程图）经构建期内联进 5 个技能正文；二者被 5 技能共享，改动爆炸半径大。

**影响链**：`tr-impl-debug.ts` → `registry.ts:120` 注册（`WORKFLOW_PAIRS`）→ `skills/` 静态快照（`pnpm generate:skills` 重生成，`test/skills-parity.test.ts` 校验）→ `test/templates.test.ts:116,134`（debug 正文断言）与 `test/allowed-tools.test.ts:56,68`（白名单断言）。`profiles.ts:61` 的依赖注入关系 `'tr-impl-debug': ['tr-docs-requirement-doc', 'spec-verify-proposal']` 不受影响。

## Goals / Non-Goals

**Goals**:

- 让排查深度**按 bug 大小与影响范围事前分级**：大范围 bug 即便已一步定位根因，仍执行 6 维根因深度分析；小范围 bug 明确止步于常规查询
- 原 2.2.4 的事后触发保留为**升级兜底**，使轻量路径不会因分级判错而卡死
- 消除需求文档的**静默覆盖**：变更内已有需求文档时，人工填写的 `## 基本信息` 与 `## 八、评审记录` 必须逐字保留
- 保持零破坏性：既有编号、注册结构、技能总数（27）、`allowedTools`、依赖注入关系全部不动

**Non-Goals**:

- **不**修改 `venus_tr_docs_requirement_doc`（其"静默覆盖"规则属 standalone 场景的合理设计；本次只在 debug 侧增加调用方判定）
- **不**同步另三处同构逻辑（`tr-impl-workflow` / `tr-impl-auto-workflow` / `tr-impl-genfull`）——**记录为已知落差**，另行变更处理
- **不**修改共享模块 `prompt-gate.ts` / `flowchart-gate.ts`
- **不**修改 `deriveCommandContent` 派生器（16 符号爆炸半径，7 个 spec-* 指令依赖）
- **不**让分级影响 2.5 缺陷链路图（`add-flowchart-cross-verify` 确立的不变量保持）
- **不**在本次重建 CodeGraph 索引（索引陈旧属既有环境问题，非本变更引入）

## Decisions

### D1: 分级步骤的位置与编号 —— 十进制插入 `2.2.3.5`

- **选择**: 新增 `2.2.3.5` 排查深度分级，位于 2.2.3 与 2.2.4 之间；2.2.0–2.2.4 既有编号与语义**全部不动**
- **理由**: 三条分级信号全部产自常规查询（爆炸半径来自 2.2.3 的 `codegraph_impact`，跨模块来自 2.2.1 文件结构，根因清晰度来自 2.2.2），因此分级**必须后置于 2.2.3**；而能力记忆中 `add-prompt-validation-gate` D5 与 `add-flowchart-cross-verify` D6 两次确立"沿用十进制插入法，**不重排既有编号**"的惯例，重排会使既有文档、能力记忆与 spec 中对 `2.2.4` 的引用失效
- **备选**: ①重排为 2.2.4 分级 / 2.2.5 深度探索（否决：违反惯例、破坏引用有效性）；②并入 2.2.4 开头、不新增编号（否决：分级作为独立决策点可见性不足，且 2.2.4 标题已含"深度探索"语义，混入分级会使职责不清）

### D2: 分级信号 —— 三条客观信号 + 明确阈值

- **选择**: 任一命中即深度路径。(a) 爆炸半径：`codegraph_impact` depth ≤ 2 受影响符号数 ≥ 5 **或** 受影响文件数 ≥ 3；(b) 跨模块：受影响范围跨 ≥ 2 个模块 / 目录；(c) 根因清晰度：2.2.2 未能一步定位单一高置信根因。信号取值 MUST 可追溯至实测结果
- **理由**: 用户诉求为"根据需求大小、涉及范围"判定。(a) 是"大小"的量化代理且已有工具支撑（`codegraph_impact` 本就是 2.2.3 的既有动作，零额外成本）；(b) 是"涉及范围"的直接表达；(c) 复用既有事后判据作为信号之一，保证与原行为连续。阈值经用户在流程最终确认门裁决采信
- **备选**: ①只给信号类别不给阈值（否决：不可验证、不可回归，与"零假设"不符）；②仅以用户描述范围判定（否决：用户在流程最终确认门选择"代码库客观信号"，且描述范围不含爆炸半径这类关键成本信号）

### D3: 原 2.2.4 保留为升级兜底 —— 扩展触发条件而非新建步骤

- **选择**: 2.2.4 的内容（`codegraph_explore` + 6 维分析）与编号不变，**触发条件**由「常规查询未定位根因」扩展为「分级为深度路径 **∨** 轻量路径未定位根因」。在正文中明确"兜底是触发条件，不是新章节"
- **理由**: 2.2.4 的**内容就是**深度探索，本身不是"兜底步骤"；真正的兜底是它新增的那条触发条件。新增一个空兜底章节会产生"只为记录判定结果而存在的僵尸步骤"，违反最小改动原则。同时该设计保证单判据与原行为**终局一致**
- **备选**: ①新建 2.2.5 兜底步骤（否决：引入僵尸步骤，且需重排编号）；②删除事后触发、只留事前分级（否决：分级判错时无纠偏出口，简单 bug 会被永久卡在轻量路径）

### D4: 分级与 2.5 解耦

- **选择**: 分级结果**只**影响 2.2.4 是否执行；2.5 缺陷链路图与流程最终确认门对两条路径**均强制**
- **理由**: 2.5 是 `add-flowchart-cross-verify` 刚落地的制品，其价值在于为 Phase 4 提供"异常节点 + 根因节点"的验证口径；轻量路径同样需要该口径（轻量 ≠ 不验证）。若让分级豁免 2.5，等于让"简单 bug"失去验证锚点
- **备选**: 路径 A 下 2.5 降为可选或简化（用户在 L5 裁决中否决——维持既有不变量，避免使刚归档的 flowchart 规格失效）

### D5: 信号降级仍生效（CodeGraph 不可用时）

- **选择**: `codegraph_status` 确认不可用时分级**仍执行**——信号 (a) 降级为 Grep 代理指标（受影响文件数阈值），(b)(c) 照常；诊断记录标注「信号降级」
- **理由**: (b)(c) 不依赖 CodeGraph；若因降级跳过分级，则在降级模式下丧失全部优化收益。该设计保持与既有 `2.2.0` 降级路径的**语义连续性**（降级不改变能力，只改变取证工具）
- **备选**: ①降级时一律走深度路径（否决：改变既有降级行为，且丧失优化收益）；②降级时一律走轻量路径（否决：Grep 下无法可靠判定半径，漏检风险高）

### D6: 需求文档分支判定 —— 仅判 active 变更目录

- **选择**: Phase 7.3 在深度复查后、生成前插入存在性判定；范围**仅** `openspec/changes/<change-name>/需求文档.md`（`path.join()`）
- **理由**: debug 只操作 active 变更——归档变更来源的 bug 按 `3.3` 规则会新建变更，其目录必无该文件，探测 devdocs 归档路径只会得到空结果并增加分支复杂度。路径唯一确定，无歧义
- **备选**: ①兼探 `openspec/devdocs/` 归档路径（否决：debug 不操作归档变更，探测无收益）；②复用 skill 的输出路径路由表（否决：路由表按归档状态三态分派，debug 场景只涉及 active 一态，复用属过度耦合）

### D7: 人工域白名单保护

- **选择**: 已存在时走**就地增量对齐更新**——`## 基本信息` 与 `## 八、评审记录` 为人工域 MUST NOT 覆盖（含占位符状态），`一~七` 按更新后制品重新派生；不调 skill
- **理由**: 需求文档八章节中，基本信息（需求编号/需求名称/交付时间）与评审记录由人工在评审流转中填写，是**不可再生数据**；其余章节可从 artifacts 派生，是可再生数据。以"可再生/不可再生"划界最稳定，无需 diff 比对（diff 在"人工值恰好与派生值不同"时无法区分是人工修改还是制品变更）。不调 skill 是为了绕开其"目标已存在则静默覆盖"规则
- **备选**: ①全量 diff 比对保留（否决：实现复杂、不确定性高，人工值与派生值冲突时无法判定意图）；②呈现待覆盖内容待用户确认（否决：用户裁决为白名单方案，且给 debug 收尾环节新增人工确认门会打断自动收尾定位）

### D8: 改动范围 —— 仅 debug（skill + 手写 command 双处）

- **选择**: 只改 `tr-impl-debug.ts` 的 skill 正文与手写 command 压缩正文；不改 `tr-docs-requirement-doc`；不同步另三处同构逻辑
- **理由**: 用户诉求明确限定 debug。另三处同构逻辑同步属范围扩张（改动面 ×4），且用户已在 L4 裁决中明确排除。`tr-docs-requirement-doc` 为叶模板（`codegraph_impact` 仅 2 符号），本次无需触碰
- **备选**: ①同步四处（否决：用户裁决排除）；②把"更新模式"下沉为 skill 的可选模式（否决：用户裁决为 debug 侧分支，且改 skill 需同步其余调用方）

### D9: 阈值边界取保守

- **选择**: 信号取值落在阈值边界（无法判定是否超阈）时取**深度路径**
- **理由**: 与零假设原则一致——宁可多查不漏。误走深度路径的代价是 token 消耗，误走轻量路径的代价是**漏检根因**（可能导致修复不彻底）
- **备选**: 边界取轻量路径（否决：与零假设原则相悖，漏检不可逆）

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| **skill 与 command 正文不同步** —— debug 指令正文为手写压缩版，非 `deriveCommandContent` 派生 | tasks 中 skill 正文与 command 正文列为**两项独立任务**；验收含"两版语义一致"核对；`test/templates.test.ts` 既有断言覆盖正文关键标记 |
| **分级信号阈值主观** —— 阈值由 AI 提议（用户已采信），真实项目中可能过松/过紧 | 阈值集中在 2.2.3.5 单节，后续可根据实际命中率单独调整；D9 的保守取值降低了过紧的漏检风险 |
| **就地对齐实现不稳定** —— AI 手动派生一~七章节时可能遗漏或改动人工域 | 正文写明人工域白名单与"补建缺失章节 + WARN"规则；spec 中以 4 条 Scenario 固化验收口径（含"不丢章节"与"目录不可读"分支） |
| **CodeGraph 索引陈旧**（本项目实测：43 文件未覆盖 2026-09-24 后新增文件） | 不影响本变更实施（改动集中在模板文本，Grep 已可完整取证）；降级路径写入 spec 与正文；索引重建建议另立变更 |
| **已知落差** —— 另三处同构逻辑仍会覆盖人工内容 | 在 proposal 与 design 的 Non-Goals 中**显式记录**，避免被误认为疏漏；建议后续单独变更处理 |
| **验证口径扩展** —— 2.2.4 触发条件变化可能被误读为"新增步骤" | 正文、spec 与本文档三处均明文"兜底是触发条件，不是独立步骤"；spec 场景显式断言 MUST NOT 表现为新增兜底步骤 |
