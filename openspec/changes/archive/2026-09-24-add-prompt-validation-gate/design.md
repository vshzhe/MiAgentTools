## Context

5 个工作流类技能模板的入口现状：

| 技能 | 入口 | 后果 |
| :--- | :--- | :--- |
| `venus_spec_explore` | `Input` 段后直接进入 `The Stance` | 刻意不设固定步骤，含糊输入被直接带入思考 |
| `venus_tr_impl_workflow` | 1.1 建探索文件 → 1.1.5 CONTEXT.md 检查 → 1.2 写 `## Background`（"User's initial description"） | 原始含糊输入被原样写入 Background，成为下游唯一事实来源 |
| `venus_tr_impl_auto_workflow` | Phase 1.1 同构 | 同上，且自动化程度更高、人工纠偏窗口更小 |
| `venus_tr_impl_debug` | Startup 记录 bug 描述 → Phase 1 强制复现 | 含糊 bug 描述直接转为失败测试的验收判据 |
| `venus_tr_impl_genfull` | Phase 0 初始化 → Stage 1 委派 explore | 含糊输入进入委派链后才由 explore 的 grill 兜底 |

**影响链**：含糊输入 → 探索文件 Background/Decisions → proposal `## Why` → design `## Decisions` → specs 需求 → tasks → 代码。偏差在链路末端才暴露，返工成本随阶段递增。

**可复用资产**：`docs/prompt.md`（提示词优化器的补全要素与输出格式约定）、`venus_spec_explore` Guardrails 既有歧义分级阈值（实质歧义必问 / 细节歧义可假设）、CONTEXT.md 既有 `蒸馏确认门` 术语（语义相邻需区分）。

**模板工程约束**：`deriveCommandContent` 被 7 个 spec-* 指令模板依赖（影响 16 个符号）；4 个 tr_impl 技能的指令正文为手写压缩版，需与技能正文同步；`skills/` 快照由 `pnpm build && pnpm generate:skills` 生成并由防漂移测试逐字节校验；技能总数 27 在 6+ 处测试断言。

## Goals / Non-Goals

**Goals**:

- 在 5 个技能的探索动作之前，统一设置「提示词校验门」，把提示词级偏差拦截在链路起点
- 清晰输入零打扰：不引入用户可感知的额外确认轮次
- 不明确输入强约束：优化后必须经用户确认，未确认不得探索
- 优化过程不篡改用户原始意图，推断与未知必须显式标注
- 校验产出的提示词基线可落盘、可追溯，成为下游唯一语义来源

**Non-Goals**:

- 不新增独立技能（不改变技能总数 27 与 `WORKFLOW_PAIRS` 注册结构）
- 不修改 `deriveCommandContent`（避免 16 符号爆炸半径）
- 不改变 `venus_spec_explore` 的"stance not workflow"定位
- 不引入 CLI 命令、不扩大 `allowed-tools` 白名单
- 不改动既有 checkpoint 编号语义与阶段边界（门以新增子编号形式插入）
- 不为已归档变更或在途探索文件做数据迁移（`## 提示词基线` 段缺失按"门尚未执行"处理）

## Decisions

### D1: 复用方式 —— 共享文本块内联（而非独立技能）

- **选择**: 新增单一源模块 `src/core/templates/prompt-gate.ts`，build 时将门文本内联进 5 个技能正文
- **理由**: 生成的 SKILL.md 仍自包含（可单独复制使用）；不触发技能总数断言（6+ 处）与依赖注入链的连带改动；无跨技能 Skill 调用往返，门作为轻量入口步骤更合适
- **备选**: 新增 `venus_tr_impl_prompt_optimize` 技能、5 技能经 Skill 工具委派——可单独调用且与 genfull 委派风格一致，但 27→28 的断言与注册同步改动面显著更大，且为入口级检查引入委派往返不成比例

### D2: 门控强度 —— 分级门

- **选择**: 清晰 → 一句话复述理解后继续（不输出校验表、不要求确认）；不明确 → 优化 + 阻塞确认；软不明确 → 记 `[假设]` 继续
- **理由**: 与用户原始表述"如果 AI 不明确则先优化，让用户确认后再继续"一致；清晰分支零打扰防止门退化为橡皮图章
- **备选**: ①恒确认（每次都展示校验结论并等待）——打断成本过高，日常使用不可接受；②仅不明确时输出（清晰分支完全静默）——用户无法确认"AI 确实做过校验"，门的可信度与可审计性下降

### D3: 清晰度维度集 —— 需求六维

- **选择**: 目标 Goal / 对象 Object / 范围 Scope / 约束 Constraints / 验收 Acceptance / 歧义 Ambiguity；硬不明确判据为"目标/对象/范围/歧义 四维存在 ❌ 或实质 ⚠"
- **理由**: 覆盖范围、行为契约、验收三类实质不明确；技术栈、字段契约等**可从代码库推断**的信息不计入阻断项（避免把探索阶段的工作前置成用户负担）
- **备选**: ①三维精简（目标/对象/歧义）——范围与验收缺失不阻断，正是本变更要防的偏差源；②八维完整（+技术栈/契约、+冲突检测）——字段与契约应由探索阶段从代码库得出，前置要求用户提供会造成不必要阻断

### D4: `venus_spec_explore` 的接入强度 —— 条件触发

- **选择**: 门以条件触发方式接入（含糊时激活，清晰则直通），不改变其"没有固定步骤、没有强制产出"的定位
- **理由**: explore 的定位明确是 stance 而非 workflow；强制门会把一个刻意的非流程技能改造成流程技能，并需要连带修订其定位表述
- **备选**: 与 4 个流程技能一致的强制门——一致性最高，但与既有定位冲突，代价大于收益

### D5: 门的位置 —— 探索文件创建之后

- **选择**: `tr-impl-workflow` / `auto-workflow` 置于 1.1（建探索文件）之后、1.1.5（CONTEXT.md 检查）之前，编号 1.1.2；`genfull` 置于 Phase 0 内 Stage 1 委派之前；`debug` 置于 Startup 段内 Phase 1 之前；`explore` 置于 `Input` 之后、`The Stance` 之前
- **理由**: 既有规格明确要求"调用即创建探索文件"，门若前置会因用户多轮交互而延迟文件创建，与既有 Requirement 冲突；置于其后则校验结论可自然写入探索文件的 `## 提示词基线` 段
- **备选**: 门置于探索文件创建之前——语义上更"入口"，但破坏既有 checkpoint 语义与规格约束

### D6: 维度参数化渲染（而非两份完整流程文本）

- **选择**: `buildPromptGateBlock(dimensions)` 渲染共享的 Step 1–5 流程文本，仅维度表按场景注入；`REQUIREMENT_DIMENSIONS` / `BUG_DIMENSIONS` 为两套常量
- **理由**: 需求版与 bug 版仅 Step 1 的维度表不同，Step 2–5（约 25 行）完全复用；两份完整文本会产生重复维护点
- **备选**: 导出两个完整文本常量——实现更直白，但流程文本重复两份，后续修订需同步两处

### D7: `debug` 采用 bug 五维

- **选择**: 症状 / 复现步骤 / 期望 vs 实际 / 环境 / 歧义；硬不明确判据为"症状笼统 + 无复现线索，或期望与实际混淆，或存在时好时坏类实质歧义"
- **理由**: debug 的输入是缺陷描述而非需求，套用需求六维（范围/约束/验收）会系统性误判；五维直接对齐 Phase 1 复现的验收判据与前置条件
- **备选**: 复用需求六维——维度与场景错配，且 bug 描述天然简短，会频繁误触发优化分支

### D8: 基线落盘段名与下游语义

- **选择**: 探索产物新增 `## 提示词基线` 段，同时记录「原始提示词」与「确认后的提示词基线」；下游以基线为唯一语义来源，基线变更须回到本门重新确认
- **理由**: 保留原始输入可追溯（判断偏差究竟是用户原本含糊还是优化引入）；"基线变更须回门"防止探索中途悄悄漂移语义
- **备选**: 仅记录优化后基线——丢失原始输入，无法审计优化是否篡改意图

### D9: 幂等（genfull → explore）

- **选择**: genfull Phase 0 产出基线后，Stage 1 委派的 explore 检测到既有基线即直接进入探索，不重复校验或确认
- **理由**: 委派链上重复确认会让用户在同一提示词上连续确认两次，属明显体验缺陷
- **备选**: 不处理幂等——实现更简单，但 genfull 路径上的用户会遭遇重复门

### D10: 门的入口形态适配

- **选择**: 门以"用户最终提供的需求描述"为唯一校验对象，并适配三种入口形态——①**无输入**（`venus_spec_explore` 允许不携带参数进入探索模式）：无可校验提示词，跳过本门直接进入探索立场；②**输入为变更名**（`/venus:spec-explore <change-name>`）：以该变更的既有制品为校验与探讨对象，不把变更名当提示词评估清晰度；③**流程技能参数缺失**（workflow / auto-workflow / debug 先交互收集主题）：以收集后的描述为校验对象，不对空输入执行校验
- **理由**: 校验门若假定"总有提示词"，会在合法入口上产生荒谬行为——把 `add-auth-system` 这种变更名判为"对象不明确"，或在用户尚未描述任何内容时要求其先补全提示词。这些入口在 5 个技能的既有 `Input` / `Startup` 段中均已存在，门必须与它们对齐
- **备选**: 不处理入口形态（假定门只在有参数时生效）——实现更短，但 `spec-explore` 的无参数入口与变更名入口都会落入误判路径，属真实缺陷而非边界假设

### D11: 门的死锁防护（显式授权按推断继续）

- **选择**: 门的确认分支新增一条出口——用户在门上明确授权按推断继续（如"你按你的判断来"）时，将全部推断项标 `[推断]` 并记入基线后继续探索，MUST NOT 反复要求确认
- **理由**: 「阻塞等待确认」是门强度的来源，但若无出口，用户一旦不愿逐项裁决（含糊输入下常见），门就会把流程永久卡在等待态——比不做校验更糟。用户拒绝优化（回到原始理解）与显式授权（按推断继续）是两种不同的合法裁决，须分别有出口
- **备选**: 只保留"用户拒绝优化"出口——用户若既不愿优化也不愿按原理解（想按 AI 推断走）将无处可去，形成死锁

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| 门被当作橡皮图章：AI 出于保守把大多数输入判为"清晰"，门形同虚设 | 硬不明确判据绑定具体信号（只有笼统动词 / 对象不可定位 / 边界开放 / 无验收判据），并要求不明确分支必须真正阻塞（未确认不得探索）；`## 提示词基线` 落盘使每次判定可审计 |
| 优化过程引入用户未提出的需求，把偏差从"含糊"升级为"错误的明确" | 门文本显式写入"不篡改用户原始意图、不擅自增加额外需求"；推断内容强制标 `[推断]`、未知标 `[待确认]`；保留原始提示词供对照；用户拒绝优化时按其原有理解继续 |
| 5 份 SKILL.md 各含一段同源文本，快照体积增大 | 单一源内联保证不产生维护分叉；指令版使用压缩块而非全文；门文本以维度表为主、流程文本精简 |
| 4 个手写指令正文与技能正文不同步（漂移） | 压缩块 `PROMPT_GATE_COMPACT` 同属单一源；技能正文内联完整块，指令正文引用压缩块，二者来自同一文件 |
| 门在 debug 场景过度触发（bug 描述天然简短） | 采用 bug 五维并把硬不明确判据限定为"症状笼统 + 无复现线索"等实质缺陷；精确环境版本号等细节歧义归为软不明确 |
| 探索中途基线被悄悄改写，下游基于漂移语义工作 | 门文本明确"基线变更 MUST 回到本门重新确认"；下游 artifact 以基线为唯一语义来源 |
| 新增子编号打乱既有 checkpoint 阅读顺序 | 编号取 1.1.2（介于 1.1 与 1.1.5 之间），不重排既有编号；`genfull` / `debug` 以段内插入方式不新增顶层 Stage/Phase |
