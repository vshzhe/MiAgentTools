# Design: iagent-legacy-migration

## Context

迁移的必要性来自既有实现的过滤方式：src/commands/uninstall.ts 与 src/core/reconcile.ts 均以 `dirName.startsWith(SKILL_PREFIX)` 判定产物归属，指令侧以 `<tool.commandsDir>/<TOOL_COMMANDS_SUBDIR>/` 定位目录。iagent-rebrand 把这两个常量改为新值后，旧前缀产物对这两个命令完全不可见——既不会被清理，也不会被提示，是设计上的盲区而非实现缺陷。

配置侧的迁移风险更高：.venus/config.yaml 的 context 是用户手写的项目背景多行块，rules/ 下是其自写的项目约束行，scan-baseline.json 是项目预扫描基线。这些内容不随技能重生成而恢复，静默失效即等于数据丢失。

迁移需要处理的数据形态（以本机现状为例）：
  .venus/config.yaml        context 多行块 + rules 列表（tr_impl/tr_test/spec）+ workflows 列表 + tools 列表
  .venus/rules/tr_impl.md   用户自写规则行（含 # 注释行）
  .venus/rules/tr_test.md   同上
  .venus/scan-baseline.json 项目预扫描基线
  <tool>/skills/venus_*     27 个旧技能目录
  <tool>/commands/venus/    27 条旧指令文件

类型改名映射（rules 列表项与规则文件名共用）：
  tr_init→init  tr_impl→impl  tr_test→test  tr_commit→commit  tr_review→review
  tr_release→release  tr_tools→tools  tr_docs→docs  spec→spec（不变）

技能与指令的旧→新一对一映射由 agent-tool-identity 能力的「旧新标识映射表」需求提供。对**清理**而言只需匹配旧前缀即可，无需逐项映射（27 项全部删除，且前缀匹配还能覆盖用户用 generate 生成的旧产物）；该需求在代码中的唯一落点是本变更新增的 `LEGACY_WORKFLOW_ID_MAP`（27 项，见 D10），其余位置 MUST NOT 再立第二份映射。

## Goals / Non-Goals

**Goals**:
- 消除旧产物孤儿：旧配置目录、旧前缀技能与指令在迁移后不再残留
- 配置内容零丢失：用户自写的 context 与 rules 行逐字保留，不被 YAML 重新序列化破坏
- 用户可感知：迁移做了什么、删了什么、可能丢失什么，全部在输出中可见
- 可安全重入：重复执行 init/update 不产生副作用，也不重复输出迁移段落
- 边界不阻断：迁移的任何异常都不应使 init/update 失败

**Non-Goals**:
- 不提供旧产物的自动备份（按已定决策，旧技能一律删除；备份目录需用户手动清理且会在下次 init 造成重复备份）
- 不保留旧前缀产物的兼容读取（新旧不并存，避免指令名冲突与两套口径）
- 不迁移用户手工修改过的技能正文内容（该内容随旧技能一并删除，仅以告警提示）
- 不改变 uninstall 与 reconcile 对非旧前缀产物的既有行为
- 不做跨机器或跨仓库的批量迁移（不新增批量/远程迁移命令）

## Decisions

### D1: 迁移内置于 init/update 入口，而非独立命令
- **选择**: 在 `iagent init` 与 `iagent update` 的入口处内置迁移步骤，先于配置创建与产物生成执行
- **理由**: 迁移的唯一可靠触发点是用户必然会执行的入口。把它们放在 init/update 路径上，使用户无需知道迁移存在即可完成升级。
- **备选**: 新增独立命令 `iagent migrate --from venus`——被否决：用户的习惯是直接敲 init/update，独立命令会被跳过，恰好留下本变更要消除的孤儿产物与静默失效的配置；在 uninstall 中兼容旧前缀——被否决：只解决清理，不解决配置搬运，且要求用户先知道要跑 uninstall

### D2: 旧技能与指令一律删除（含手工修改过的）
- **选择**: 匹配旧前缀的技能目录与指令目录整体删除，不区分是否被用户手工修改过
- **理由**: 重命名的心智是「新名取代旧名」，新旧并存造成的困惑大于保留的价值。丢失风险以显式告警而非保留物来对冲。
- **备选**: 检测到指纹/版本不匹配（手工修改）时保留并提示——被否决：新旧技能并存会使技能清单与指令补全列表出现两套相似条目，且旧条目永不更新，长期污染用户环境；用户已明确选择一律删除；先备份到 .iagent-backup/ 再删除——被否决：备份目录需用户手动清理，且下次 init 需额外判定以避免重复备份，复杂度换来的收益不确定

### D3: 配置搬运采用逐行段替换，不重新序列化 YAML
- **选择**: 复用 project-config.ts 中 replaceConfigSection 的语义：只替换命中的目标段（rules 列表），其余行含注释与未知段逐字保留
- **理由**: context 是自由多行文本、rules 是列表、且用户可能在其中留有注释；逐行段替换是唯一能保证逐字保真的方式，且与既有配置回写路径行为一致。
- **备选**: 解析 YAML 后整体重新序列化写入——被否决：会丢失用户注释与未知段，且与既有实现（replaceConfigSection 的文件头注释已明确 MUST NOT 重新序列化）相冲突

### D4: 幂等判定依据：无旧物即静默跳过
- **选择**: 当 `.venus/` 不存在且未发现任何旧前缀产物时，静默跳过迁移且不输出迁移段落
- **理由**: 迁移是幂等的一次性动作；判定依据取「旧物是否存在」这一客观事实，无需额外的状态文件记录，也避免了状态文件自身成为新的需要维护的产物。
- **备选**: 总是输出「迁移已完成」——被否决：对全新项目与已升级项目是纯噪声，会使 init 输出膨胀

### D5: 配置解析失败时保留原物并告警，不阻断主流程
- **选择**: `.venus/config.yaml` 解析失败时，不删除原文件、不写入半成品 .iagent/，输出告警后继续 init/update 主流程
- **理由**: 迁移是升级的辅助步骤，其失败不应阻塞主流程；保留原物可使用户手工修复后重跑迁移。
- **备选**: 解析失败即中止 init/update——被否决：用户将无法升级，而解析失败可能只是格式个别偏差，代价与收益不成比例；解析失败仍写入能解析的部分——被否决：会产生内容残缺的 .iagent/config.yaml，比保留原物更危险

### D6: 迁移先于 reconcile 执行
- **选择**: 迁移步骤在 init/update 的产物扫描（reconcile）之前完成
- **理由**: 先清理再扫描，使 reconcile 的输出只反映真实的新口径状态。
- **备选**: 迁移后置——被否决：旧产物会先被 reconcile 报为「不在当前 workflows 配置中」的孤立产物，产生误导性提示

### D7: 既有新配置目录不覆盖
- **选择**: `.iagent/config.yaml` 已存在时保留既有内容并告警，不搬运不覆盖；旧配置目录同时保留不删
- **理由**: 配置目录在本项目的既有语义是「已存在即视为用户资产，只补缺失的规则文件、不覆盖」。迁移作为辅助步骤必须沿用同一语义，否则会在升级路径上引入与 init 相互矛盾的行为。
- **备选**: 无条件覆盖为新搬运内容——被否决：用户可能已按新口径自建并写入项目约束，覆盖即数据丢失，且与既有 ensureProjectConfig 的「已存在则保留」语义相矛盾；覆盖但先备份 .iagent/config.yaml——被否决：引入备份目录的清理负担，且用户已明确不采用备份方案

  搬运成功时旧配置目录的处理：`.venus/` 内**全部**条目搬运完成后即删除该目录（报告记入删除项），存在未处理项（规则文件目标已存在、rules/ 下有子目录、顶层有非预期条目）时保留目录并告警。删除是幂等性的前提——目录留存会让每次 init/update 都重新判定为「有旧物」并重复输出报告；「搬运」语义本身也是源端消失。搬运失败（解析/读取异常）时目录同样保留，供修复后重跑。

### D8: 删除边界安全与空 commandsDir 跳过
- **选择**: 删除前校验目标位于工具目录的对应子目录之下；不跟随符号链接；清理后移除空目录；commandsDir 为空字符串的工具跳过指令侧清理
- **理由**: 迁移是自动执行的删除动作，触发时机不由用户主动选择，因此边界必须由代码强制而非依赖路径恰好正确。伴生变更已在 uninstall 与 reconcile 中固化同一守卫，本变更沿用以免出现两套行为。
- **备选**: 直接 rmSync 目标路径不做校验——被否决：`path.join(root, '', 'venus')` 会得到项目根下的 venus/，一旦成立即删除与本工具无关的用户目录，属不可逆事故；跟随符号链接递归删除——被否决：链接目标可能位于工具目录之外，越界删除风险

### D9: 旧版品牌产物清理纳入迁移
- **选择**: 迁移 SHALL 清理四类旧版品牌产物：旧补全脚本文件与 rc/profile 旧标记块、变更目录下旧遗留 sidecar 目录、旧跨变更索引目录。清理范围由伴生变更的「品牌命名的磁盘产物一同改名」需求界定，两侧使用同一份旧值常量
- **理由**: 旧补全产物的残留有两个直接后果：rc 中的旧标记块因不被新标记常量识别而无法卸载，且仍会 source 旧脚本使补全列表出现重复项与冲突项。仓内旧 sidecar 与索引目录则会在新工具下成为不可见孤儿。四者同属「品牌改名的遗留物」，与技能产物清理同源，归入同一迁移入口最自然。
- **备选**: 清理不实现，由用户手工处理——被否决：旧 rc 标记块继续 source 旧补全脚本会造成补全项重复与冲突，用户难以自行定位；且这些产物分散在用户主目录与仓内目录两处；由伴生变更自行清理——被否决：该变更按已定原则不承担迁移职责，且其任务清单已冻结；迁移是唯一统一入口

### D10: workflows 列表按旧→新映射改名（实施期修订）
- **选择**: 搬运 config.yaml 时，除 rules 列表按类型改名外，`workflows:` 列表项 SHALL 按 `LEGACY_WORKFLOW_ID_MAP`（27 项旧指令 id → 新指令 id）改写。该表是本变更新增的代码产物，承载 agent-tool-identity 的「旧新标识映射表」需求，为唯一真源
- **理由**: 旧配置的 workflows 存的是**旧指令 id**（`tr-impl-feature`、`tr-tools-pwd`…）。`getSkillTemplates` 按 `commandId` 过滤生效集，原样搬运会使生效集匹配不到任何模板 —— 搬运后首次 init 装 0 个技能，旧用户升级即工具失效，与 Goal「配置内容零丢失」直接冲突。改名是让用户既有选择继续生效的唯一办法
- **备选**: 原样搬运并仅告警——被否决：把「用户手工修一遍配置」当作默认升级路径，代价与收益不成比例；原样搬运不告警——被否决：静默失效；丢弃旧 workflows 列表改用默认集——被否决：丢失用户选择，且与「不丢项」相悖
- **对原措辞的修订**: 原 design.context 与 task 1.1 的「不另立第二份映射」表述，在本实现中收敛为「`LEGACY_WORKFLOW_ID_MAP` 是该映射表的唯一代码真源」——旧产物的**删除**仍不依赖该表（按旧前缀整体清理，前缀匹配还能覆盖用户 generate 出的旧产物），故不存在第二份映射或第二份删除清单

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| 用户手工修改过的技能正文在迁移中被删除且未提前知情 | 迁移报告中显式列出被删除的技能与指令明细，并附告警说明其中可能包含的手工修改；在 CHANGELOG 与 docs 的升级指引中提前说明该行为 |
| 误删非本工具产物：以旧前缀匹配时若前缀过宽，可能命中用户自建的同名目录 | 仅删除以旧技能前缀开头的技能目录，以及旧命名空间子目录下的指令文件；非旧前缀产物完全不触碰；单元测试覆盖「同名但非旧前缀」的保留断言 |
| 配置搬运丢失用户规则：rules 列表改名与规则文件名改名若只完成一处，会造成规则静默失效 | 两者在同一迁移步骤内成对改写，并以测试断言迁移后 config 的 rules 列表与 rules/ 下文件名一一对应且无 missingRuleFiles |
| 迁移异常阻断 init/update 主流程 | 迁移整体以容错包裹，任何异常降级为告警并继续主流程；边界场景（.venus 缺失、解析失败、部分存在）纳入测试矩阵 |
| 重复迁移造成副作用（如重复删除或重复写入） | 以「旧物存在性」作为唯一判定依据；幂等场景（连续执行两次）纳入测试矩阵，断言第二次零副作用且无迁移输出 |
| 跨变更顺序依赖：本变更引用的新 token 与映射表由 iagent-rebrand 定义，若反序实现会引用到不存在的常量 | 在 tasks 与 proposal 中显式标注本变更依赖 iagent-rebrand 先落地；实现顺序不允许颠倒 |
| 越界删除（不可逆）：工具适配配置中 codex 的 commandsDir 为空字符串，path.join(项目根, '', 子目录) 会得到项目根下的同名目录；迁移遍历若照抄该拼接模式，会删除与本工具无关的用户目录 | 对 commandsDir 为空字符串的工具跳过指令侧清理；删除前校验目标位于该工具目录的对应子目录之下，越界即拒绝并记入跳过项；伴生变更已在 uninstall 与 reconcile 中固化同一守卫 |
| 覆盖用户已自建的新配置：用户可能已按新口径建立 .iagent/ 并写入项目约束，无条件搬运会覆盖其内容 | 新配置目录已存在时保留既有内容并告警，旧配置目录同时保留；与 ensureProjectConfig 的「已存在则保留」语义对齐 |
| 符号链接导致越界删除：旧前缀技能目录可能是指向工具目录之外的符号链接，递归删除会连带删除链接目标 | 删除时不跟随符号链接，仅移除链接本身；纳入安全边界测试矩阵 |
