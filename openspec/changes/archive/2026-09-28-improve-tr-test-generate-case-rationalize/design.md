### 架构现状

`venus_tr_test_generate` 是**唯一真源**的测试能力技能，采用多 schema 模式：

| 层 | 位置 | 职责 |
|---|---|---|
| 主 SKILL | `src/core/templates/workflows/tr-test.ts` → `getTrTestGenerateSkillTemplate().instructions` | 语言无关：schema 路由、BCDE、分层策略、编写规范、反模式 |
| references | 同文件 `SCHEMA_JAVA` / `SCHEMA_NODE` 常量 | 语言专属：框架判定、模板、命令、语言约束 |
| 快照 | `skills/venus_tr_test_generate/` | 静态快照，由 `pnpm generate:skills` 生成，**禁止手编** |

而编排侧（四个模式 + 交互式工作流）分布在三处：

| 模式 | 模板 | 消费的测试能力 |
|---|---|---|
| propose | `spec-propose.ts` | **无**（F8） |
| apply | `spec-apply.ts` | **无测试关卡**（F10，Step 8 用 `-DskipTests`） |
| auto-workflow | `tr-impl-auto-workflow.ts` | **无**（F11，继承 apply） |
| debug | `tr-impl-debug.ts` | 自研回归测试，**未委派**（F12） |
| 交互式工作流 | `tr-impl-workflow.ts` | **无**，且 skill/command 双份正文手工维护（F17） |

### 关键约束（AGENTS.md 修改守则）

1. 改模板后必须 `pnpm build && pnpm generate:skills`，否则 `test/skills-parity.test.ts` 失败
2. 改模板正文命令需同步 `allowedTools`，否则 `test/allowed-tools.test.ts` 拦截
3. 版本号按改动性质递增（改技能模板行为 → **minor**）+ CHANGELOG 随本次提交
4. `spec-*.ts` 的 command 版由 `deriveCommandContent()` 派生（单一源），**禁止另立手工字符串**
5. `tr-impl-workflow.ts` 与 `tr-impl-debug.ts` 未纳入单一源机制 → skill/command 双份手工同步

## Goals / Non-Goals

**Goals**:

- 使测试成为**规划 → 执行 → 验证**全链路的一等公民：propose 可规划、apply 可执行、auto-workflow 可自动通关、debug 可复用生成能力
- 消除 `venus_tr_test_generate` 中会**直接传导错误**的规则缺陷（BCDE 示例标注矛盾、固定配额驱动凑数）
- 让"减少低价值用例"有可执行的机制（不测清单 + 优先级分级），而非仅停留在原则描述
- 统一 `[测试]` 标签口径，使 tasks.md 中的测试项可被 CLI 统计、被提交技能分类、被归档技能标注
- 修复发现的能力 spec 漂移（FIRST 原则实现缺失、分层指南 Node 写死）

**Non-Goals**:

- **不反转流程顺序**（不做 TDD）——用户明确 Q2 选择"四种模式模板的自身改造"，保持既有"先实现后测试"的编排顺序
- 不新增技能、不新增技能类型（`SKILL_TYPES` 不变）
- 不把测试关卡做成硬阻塞式门禁——存量红测试不计入本次失败
- 不实现 delta spec 合并逻辑到 CLI（仍由 AI 技能执行）
- 不修改 `.venus/rules/ai-coding.md` 的既有约束

## Decisions

### D1: 测试能力真源唯一化，编排侧只做"引用"

- **选择**: `venus_tr_test_generate` 保持唯一真源；propose/apply/auto-workflow/debug/交互式工作流通过**委派（Skill tool）**或**语义引用**消费其能力，MUST NOT 各自实现测试规则
- **理由**: 现状 debug 自研、其余为零（F8/F10/F11/F12），规则分散必然漂移。唯一真源使框架检测、既有风格对齐、BCDE 覆盖、反模式防护一次沉淀多处复用
- **备选**: 各模式模板内各自写测试规则（否决——五处重复维护，已有 F9 三处口径不齐作为前车之鉴）

### D2: 测试层级与语言 schema **正交**，用章节而非新文件承载

- **选择**: 在 `tr-test.ts` 阶段一新增「1.3 测试层级路由」章节，层级取值为单元/功能级；功能级的具体写法下沉到各 schema 的新增小节
- **理由**: 用户 Q3 选"两者都要"。若新增 `references/schema-functional.md`，会与 schema-java/node 形成 **2 语言 × 2 层级 = 4 文件**的二维爆炸，且功能级测试（`@SpringBootTest`/supertest）本身就是语言专属内容，天然属于既有 schema
- **备选**: 新增独立 `schema-functional.md`（否决——内容与既有 schema 重叠，维护成本翻倍）

### D3: `[测试]` 标签为**第五类一等任务类型**，含层级与优先级子标注

- **选择**: 标签集扩为 `[代码]`/`[测试]`/`[DB脚本]`/`[使用说明]`；`[测试]` 带子标注 `[单元]`/`[功能]` 与 `[P0]`/`[P1]`/`[P2]`，形如 `- [ ] [测试][单元][P0] 3.1 ...`
- **理由**: 修 F9（`tr-commit-push.ts:64` 已假设 `[测试]` 存在但无模板产出）；使测试在 tasks.md 中可勾选、可统计（`venus spec status`）、可被提交技能分类（路径规则优先，标签为辅助）
- **备选1**: 复用 `[代码]`（否决——测试代码与生产代码在提交分类、验证方式、批次依赖上均不同）
- **备选2**: 子标注用独立标签如 `[单元测试]`（否决——标签集膨胀，且层级/优先级是两个正交维度，组合会爆炸）

### D4: 测试关卡与编译检查**分离**，紧跟其后

- **选择**: `spec-apply.ts` Step 8 编译检查保持 `-DskipTests`；在其后新增 Step 9「测试执行关卡」，然后原 Step 9 收尾顺延
- **理由**: 二者失败语义不同——编译失败是硬错误（代码根本不能构建），测试失败可能是存量红、断言不符或环境问题，需要不同的处置分支与用户选项。合并会使失败归因困难
- **备选**: 并入编译检查（一起跑 `mvn test`）（否决——失败语义混淆，且 `-DskipTests` 的既有语义被破坏）

### D5: 测试关卡的判定边界 = **仅变更范围，存量红不阻塞**

- **选择**: 关卡只运行 `[测试]` 任务产出的测试文件 + 变更文件的对应既有测试；范围外失败仅 WARN
- **理由**: 用户 L5 裁决。存量测试已红的项目很常见（探索记录「边界场景」已列此风险），全量判定会让 apply 在存量红项目上完全不可用，反而促使绕过关卡
- **备选**: 跑全量并做失败归类（否决——需实现"失败归类"逻辑，复杂度高且归类本身可能误判）

### D6: 覆盖度度量采用**实测优先 + 静态矩阵降级**

- **选择**: 有 JaCoCo/c8 时输出实测行覆盖与分支覆盖；无工具链时降级为「specs Scenario → 用例」映射矩阵，并**强制标注"未实测"**
- **理由**: 用户 L2 裁决。静态矩阵直接对齐提案的验收标准（每个 Scenario 是否被用例覆盖），且无工具依赖——这对本仓库这类"产物是 Markdown"的场景尤其必要（无代码行可覆盖）
- **备选**: 纯实测（否决——无工具链项目完全失效）；纯静态（否决——放弃可得的硬数据）
- **风险控制**: 强制标注"未实测"是为了防止降级结果被误读为实测覆盖度

### D7: 优先级分级**影响生成决策**，而非仅作标注

- **选择**: P0 必生成 / P1 默认生成 / P2 需显式确认才生成
- **理由**: 用户 L4 裁决。仅标注不改变行为，则"减少低价值用例"没有执行手段；把 P2 的生成权交给用户确认，是把"减少低价值用例"落成机制的关键
- **备选**: 仅标注（否决——分级沦为装饰）；分级决定测试深度（否决——与 BCDE 修正叠加后规则过于复杂，且深度应由被测对象复杂度决定而非优先级）

### D8: FIRST 原则按"补回实现"处理，spec 漂移按"实现为准"修订

- **选择**: FIRST 原则的需求**保留**（spec 已声明 SHALL），把丢失的实现补回 `tr-test.ts`；分层测试指南的 Node 写死表述**改为语言无关**（这是 spec 侧的表述问题）
- **理由**: F6/F7。FIRST（Fast/Independent/Repeatable/Self-validating/Timely）与本次"用例合理化"目标同向，属于实现漏做而非需求过时——删除它会放弃一个有效约束
- **备选**: 删除 FIRST 需求（否决——放弃有效质量约束）

### D9: 不测清单**显式留痕**，而非静默跳过

- **选择**: 不测清单涉及的被测对象，技能输出"已评估、判定不生成测试"的结论与依据；生成报告同时含"已生成"与"判定不生成"两类清单
- **理由**: 静默跳过会使"没写测试"与"没评估过"无法区分——这正是本次要解决的模糊性来源。同一原则也适用于 P2 未确认的用例
- **备选**: 静默跳过（否决——掩盖决策过程）

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| **固定配额改分级会减少生成用例数**，可能被误读为"能力退化" | 这是预期效果（用户 Q1 明确要求"减少低价值用例"）。技能文档同步说明取舍依据；报告输出"判定不生成的目标及依据"使减少可见且可追溯 |
| **`tr-impl-workflow.ts` 双份正文漏改其一**（F17，该文件 2276 行且未纳入单一源机制） | tasks.md 中为 skill 版与 command 版**各列一个独立任务**（不合并为一个"改 tr-impl-workflow"任务），使遗漏在勾选时可见；spec 中已声明"两版正文 MUST 同步"作为验收口径 |
| **任务格式在 6 处硬编码**（F15），漏改会导致技能正文与 CLI 模板指令冲突 | tasks.md 按文件逐条列任务（不按"改标签"聚合）；新增单测断言 `TASKS_TEMPLATE` 含 `[测试]` 标签，防止未来回归 |
| **测试关卡在存量红项目上误伤** | D5 已限定仅变更范围；范围外失败仅 WARN。spec 中为该行为设专门 Scenario（"存量失败测试不阻塞"）作为验收口径 |
| **功能级测试在小项目无工具链**，生成不可运行的代码 | spec 中设专门 Scenario（"项目缺少功能级测试工具链"）要求降级为单元测试并提示，MUST NOT 生成无法运行的代码 |
| **覆盖度降级结果被误读为实测数据** | spec 强制要求降级时标注"未实测"（D6） |
| **`-DskipTests` 被误改**导致编译检查与测试关卡职责混淆 | design 明确 D4；A3 节点在流程图中标注"保持"，tasks.md 中不列该改动项 |
| **快照未重生成导致 CI 失败** | tasks.md 末位单列 `pnpm build && pnpm generate:skills` 任务，并有 `test/skills-parity.test.ts` 兜底 |
| **版本号/CHANGELOG 遗漏**（AGENTS.md 第 8 条） | tasks.md 单列版本与变更日志任务，标注递增位为 minor |
