审查代码 —— 按维度检查，只报告经过验证的问题，严重程度分级呈现。

## 审查维度

按以下维度逐一检查（顺序即优先级）：

1. **正确性**：逻辑错误、边界条件遗漏、空指针风险、异常分支缺失
2. **安全性**：SQL 注入（${} 拼接）、未校验输入入库、敏感信息泄露、越权访问
3. **性能**：循环内数据库/Redis 请求、重复计算、集合未指定初始容量、不必要的对象创建
4. **可维护性**：命名见名知意、方法职责单一、重复代码、魔法数字
5. **规范符合度**：分层是否越界（Controller 直接调 DAO）、对象是否混用（Entity 直接返回前端）、过期 API 使用

## 执行步骤

1. **确定审查范围**

   - 用户指定了文件/分支/PR：按指定范围
   - 未指定：运行 `git diff` / `git diff --cached` 审查未提交变更；工作区干净时提示用户指定范围

2. **通读代码**

   - 先理解意图再挑毛病：读关联的调用方与被调方
   - 对照项目自身规范（CLAUDE.md、已有代码风格）而非个人偏好

3. **验证每个发现**

   - **只报告能指出具体行号、并说明触发场景的问题**（什么输入/状态 → 什么错误结果）
   - 拿不准的问题标注"待验证"并说明验证方法，不当作确定结论

4. **输出审查报告**

   按严重程度分组：

   | 级别 | 含义 |
   | :--- | :--- |
   | CRITICAL | 必须修复：正确性缺陷、安全漏洞 |
   | WARNING | 应当修复：性能问题、规范违反 |
   | SUGGESTION | 建议改进：可读性、简化机会 |

   每条包含：文件:行号、问题描述、触发场景、修复建议。

## 约束

- 只审查不改码：发现问题列出报告，修复需用户确认后衔接 `venus_impl_feature`
- 不报告纯风格偏好（引号、空行数量）除非项目规范明确要求
- 发现优点也可以简短肯定，但重点是问题
